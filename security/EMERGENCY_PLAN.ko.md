## 현재 사실
- 콘솔 (default) 배포 규칙 전체를 backups/production-2026-11-16.rules에 전사 백업했다. 활성 버전 화면 표시는 2026-07-09 22:48. 8줄 전체를 DOM으로 읽어 확인했다. API 원본 ruleset ID는 수집하지 않았다.
- 재귀 match /{document=**} + allow read, write: if true 는 (default)의 모든 현재/미래 컬렉션 및 하위 문서에 적용된다. 인증 없는 SDK/REST 요청에 규칙상 읽기/생성/수정/삭제를 허용한다. App Check 등 별도 통제의 실제 강제 상태는 확인하지 않았다.
- 다른 데이터베이스, Storage, Realtime Database, IAM까지 이 규칙이 적용되는 것은 아니다. 별도 감사 필요.
- 운영 데이터에 대한 비인증 요청은 실행하지 않았다. 실제 유출/변조가 있었다고 단정할 증거는 없다. 감사 로그 활성 여부/보존 범위와 과거 읽기·쓰기, 트래픽, 계정 사용 이력을 별도 조사해야 한다.

## 가장 빠른 차단 (업무 중단을 감수하는 비상 경로)
예상 운영 시간: 업무 중지 확인과 별도 승인 후 게시 자체는 수 분, 전파와 검증에 추가 시간을 잡는다. Firebase 공식 문서상 새 쿼리/리스너 반영은 최대 1분, 기존 활성 리스너의 전체 전파는 최대 10분이 걸릴 수 있다. 준비된 상태에서 약 10~20분의 차단 작업 창을 잡는 운영 추정이며 완료 보장은 아니다.
출처: https://firebase.google.com/docs/firestore/security/get-started

1. 책임자에게 업무 중지/오프라인 대기열·저장 중 전표 유무 확인. 직원에게 저장 재시도 중단 안내. 승인은 별도 필요.
2. emergency-deny.rules 전체를 (default)에 배포. Firebase 클라이언트 읽기·쓰기 모두 거부. 서버 Admin SDK/IAM 접근과 이미 다운로드된 데이터는 차단/회수되지 않는다.
3. 전파 지연을 고려해 새 비인증 연결과 기존 리스너 모두 거부되는지 확인. 재접속/캐시 화면 표시와 서버 접근 성공을 혼동하지 않는다.
4. 모든 정상 사용자의 기존 방식 업무도 중단된다. 규칙 내용 준비 후 승인·전파·검증이 최소 시간의 핵심이며, 무중단 즉시 차단을 약속할 수 없다.
5. 안전한 복구는 검증된 제한 규칙 + 인증된 앱 + 승인된 UID 매핑으로만 진행. 공개 규칙 복원은 재노출이므로 자동 롤백하지 않는다.

## 업무 유지 전환 (시간이 더 필요한 권장 복구 경로)
1. demo-linker-auth 에뮬레이터에서 Auth/Rules/Functions 테스트. 운영 자격증명 금지.
2. 기존 회사/직원/거래처 문서ID를 유지하는 별도 memberships UID 매핑. 실제 수신 이메일 확인, 관리자 본인 확인/명시 승인. 이메일 동일 자동 연결 금지.
3. 서버에서 계정 인증·메일 인증·회사 활성·소속 승인·역할 검증. 권한 문서는 클라이언트가 수정 불가.
4. 모든 직원·거래처·번들·백업·문의·로그에 남은 평문 비밀번호 제거 계획을 승인받아 별도 실행. 이미 노출됐을 가능성에 대비한 사용자별 비밀번호 재설정 계획 필요. 기존 비밀번호 이관 금지.
5. 대표 테스트 회사/기기, 데스크톱·모바일·PWA·오프라인 재접속 검증. 재고 수정 브랜치 통합 후 주문→상차→납품→전표 시나리오 확인.
6. 배포/마이그레이션/규칙 배포의 정확한 대상·작업 시간·복구 절차를 제시하고 각각 승인받는다.

## 충돌 경계
- DesktopApp.jsx / 모바일 App.jsx는 인증과 재고 로직이 같은 파일에 존재한다. 인증 진입/세션/가입 블록만 수정하고 업무 처리 함수는 원문과 비교한다.
- 재고/상차/전표 함수, stockUtils/productStockUtils, OrderList, SalesInvoice, bundle 재고 계산은 수정 금지.
- 모바일 feat/idempotent-inventory-transaction 변경 파일 목록과 겹침을 비교하고 자동 병합 금지. main으로 병합하거나 서비스 배포하지 않는다.

## 검증의 한계
규칙 단위 테스트 통과는 ERP 전체 통합 성공을 의미하지 않는다. 특히 기존 bundles, metadata, 설정 초기화, 거래처 포털이 새 권한 모델과 맞는지 전체 사용자 흐름 검증이 필요하다. 미검증 항목은 배포 차단 사유로 기록한다.
